## 🗂️ Topics Covered

> 🥋 A frontend app does not need its own backend to show real data: there are thousands of
> public APIs. This lesson added a `ChuckNorris` page that loads a random joke, first the old
> way with `XMLHttpRequest`, then with `fetch`, and on the way covered HTTP request methods,
> the Network tab, JSON, promises and `async`/`await`.

### 1. 🌐 Public APIs

So far the app has been a static single page application: everything is in the browser, no
server of our own. That does not stop it from using outside data. **REST APIs** (also called
web APIs) are web addresses that answer with data instead of a web page. A huge list of free
ones is at <https://github.com/public-apis/public-apis#index>: facts, pictures, weather and
much more. Some need registration or an API key (the *Auth* column), so the owner can see
what they are used for. Big platforms (Google, Azure and others) offer many more, often with
enough free credit for experiments.

APIs do not only hand out facts. The Deck of Cards API, for example, shuffles a deck and
deals cards, so you can build a card game with no backend or database of your own.

The page for today was one of the simplest: <https://api.chucknorris.io/>, random Chuck
Norris jokes. (Not all of them are clean. Fair warning.) A new file
`src/pages/ChuckNorris.vue` was enough to get a tab, thanks to last week's file-based
routing.

### 2. 🔎 Requests in the Network tab

What is the `GET` next to the API's address? DevTools (right click, Inspect) has a
**Network** tab listing every request a page makes: the page itself, styles, scripts,
pictures. Open it after the page has loaded and it may be empty; reload and it fills up.
Filtering by *Doc* shows the page requests. Clicking one shows the **request URL** and the
**request method**.

HTTP methods:

- **GET**: "give me this". Every link click and every address typed in the bar is a GET;
  parameters can go into the URL, so they are always visible. A GET can be tested just by
  opening the URL in a tab.
- **POST**: "here is some data", usually creating something new: forms, logging in, a new
  post. Plain HTML can only send GET and POST (`<form method="post">`).
- **PUT** and **PATCH**: updating. PUT sends everything again, even unchanged fields; PATCH
  sends only what changed (a new title, not the whole article).
- **DELETE**: three guesses.
- **OPTIONS**: mostly used by the browser itself, to ask whether a site allows requests
  from JavaScript.
- **HEAD**: only the headers, no content.

**Headers** carry extra information both ways. Response headers tell the browser, for
example, the `Content-Type` (a web page, a picture, a PDF...). Request headers include what
the browser accepts and prefers, like `Accept-Language` from your system settings, which a
server may (or may not) use to pick the page language.

![HTTP](https://api.memegen.link/images/buzz/HTTP_methods/HTTP_methods_everywhere.png)

### 3. 📜 JSON, and a viewer for it

The joke URL answers with **JSON**. Firefox shows it nicely; Chrome shows a raw line, so a
viewer extension helps, e.g. JSON Viewer
(<https://chromewebstore.google.com/detail/json-viewer/gbdbademeighmnbliehmnoifmabbedbp>),
which has dark themes and lets big objects and lists be folded, handy when an API returns
thousands of lines.

The joke object has `categories`, `created_at`, `icon_url`, `id`, `updated_at`, `url` (a
permanent link to this exact joke) and `value`, the joke itself. `/jokes/random` gives a new
one on every request.

**API** itself (*application programming interface*) is used for two things, which is
confusing: web APIs like this one, and the **browser APIs** described on MDN. Those are the
features browsers add on top of the JavaScript language: location, camera, microphone,
changing the page, and making requests.

### 4. 📨 The old way: `XMLHttpRequest`

Before JSON, data usually came as **XML**. HTML looks a lot like it: tags, attributes,
content. That is why the classic browser API for requests is called `XMLHttpRequest`, even
though it fetches anything. Renaming it would break half the web, so the name stayed. The
MDN example
(<https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest_API/Using_XMLHttpRequest>)
went into the page, with the URL swapped (the MDN example address does not really answer):

```js
let joke = ref('');

function reqListener() {
  joke.value = JSON.parse(this.responseText).value;
}

const req = new XMLHttpRequest();
req.addEventListener("load", reqListener);
req.open("GET", "https://api.chucknorris.io/jokes/random");
req.send();
```

Step by step: `new` creates a request object, a `load` listener waits for the answer,
`open` sets the method and URL, `send` sends it. In the listener, `this` is the request and
`responseText` is the answer **as text**. `JSON.parse` turns it into an object; `.value`
picks the joke. The usual slip: assigning to `joke` instead of `joke.value` replaces the
ref and the page stops updating.

It works, but it is long, and this is the simplest kind of request.

### 5. ⏳ `fetch`, promises and the single thread

The modern replacement is **`fetch`**
(<https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch>). Logging its
result shows something odd: not a response but a **Promise**, a promise that an answer will
arrive at some point.

Why? JavaScript runs in a **single thread**: it does one thing at a time. While it is busy,
nothing else on the page happens. An endless loop freezes the whole tab: no button works,
not even the CSS finishes loading, until the browser offers to kill the page. Waiting for
the network that way would be terrible. The browser can do things in parallel, so it takes
the request off JavaScript's hands, works on it in the background, and the promise is
fulfilled when the answer comes.

![Single thread](https://api.memegen.link/images/disastergirl/while(true)_in_the_page/The_whole_tab_freezes.png)

The first way to use a promise is `.then(...)`, which gets the function to run when it is
fulfilled. `res.json()` reads the body as an object, and is a promise too, so the `then`s
chain one after another. One request is fine, but when each request depends on the previous
answer, five or six levels of functions inside functions become **callback hell**, hard to
read and easy to break with one missing bracket.

### 6. 🧘 `async` / `await` and `<Suspense>`

The cleaner way is **`await`**: "wait here until the promise has its answer", without
freezing the page. Normally `await` is only allowed inside an `async` function. In
`<script setup>` it can be used directly, but then the component itself becomes
asynchronous, and Vue asks for its parent to wrap it in **`<Suspense>`**. Since every page
goes through the router, the wrapper went around `RouterView` in `App.vue` (no import
needed):

```html
<div class="container content mt-2">
    <Suspense>
        <RouterView />
    </Suspense>
</div>
```

With that, the whole XHR example shrank to:

```js
let joke = ref('');
let url = "https://api.chucknorris.io/jokes/random";
const res = await fetch(url);
const json = await res.json();
joke.value = json.value;
```

It reads top to bottom like ordinary code (request, then JSON, then the joke), while in the
background it still runs alongside everything else.

![Then vs await](https://api.memegen.link/images/pooh/then_inside_then_inside_then/await,_await,_await.png)

How JavaScript juggles all this behind the scenes is tricky even for working developers.
Recommended for watching at home: a JSConf talk on the **event loop**
(<https://www.youtube.com/watch?v=8aGhZQkoFbQ>), which explains the call stack, callbacks and
how it all fits together better than words on a whiteboard. Next time: tools that make lots
of requests a bit easier.

## ✅ Takeaways

1. **Public APIs** give a frontend real data without a backend of its own.
2. **The Network tab** shows every request with its URL, method and headers. GET reads,
   POST creates, PUT/PATCH update, DELETE deletes.
3. **JSON is the usual answer format**; `JSON.parse` or `res.json()` turns it into an
   object.
4. **`XMLHttpRequest`** works but is long-winded; the name is a leftover from XML days.
5. **JavaScript is single-threaded**; the browser does requests in the background and hands
   back a **Promise**.
6. **`await` beats chains of `.then`**; top-level `await` in `<script setup>` needs a
   `<Suspense>` around the component.
7. **Watch the event loop talk** for how it all works underneath.
