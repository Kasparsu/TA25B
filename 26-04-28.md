### 2. 📦 Why Containers? — The Problem They Solve

Before going hands-on, the instructor spent time deepening the motivation for containers — expanding on real pain points that every developer eventually hits.

**Problem 1 — "Works on my machine":**
You build and test something locally. Your colleague or the production server has a slightly different environment — different OS, different version of Node.js, a library installed at a different path — and suddenly it breaks. Figuring out why can take hours or days. A container packages your app *together with exactly the environment it needs*, so it runs identically everywhere Docker is installed.

**Problem 2 — Version conflicts between projects:**
You're working on multiple projects. Project A needs Node.js 18, Project B needs Node.js 20. Or Project A needs Python 3.9, Project C needs Python 3.12. Installing multiple versions of the same tool on your machine causes conflicts, requires version managers, and clutters your system. With containers, each project has its own isolated environment — no conflicts.

**Problem 3 — Database isolation:**
If you install a database (PostgreSQL, MariaDB, etc.) directly on your machine and two different projects use it, they share the same database server. A bug in one project's migration can corrupt the database used by the other — suddenly neither project works. Each project deserves its own isolated database container.

**Problem 4 — New machine / new team member setup:**
A new developer joins the team. Without containers, they spend hours (or days) installing every dependency, configuring environment variables, and troubleshooting version mismatches. With Docker, they clone the repo, run one command, and everything is running. The setup is described in code, not in a README that's three years out of date.

> 💡 **The key insight:** containers don't just isolate running programs — they make environments reproducible, portable, and disposable. You can throw away a broken container and spin up a fresh one in seconds.

### 3. 🧠 The Kernel — Deeper Explanation

Because students asked questions, the instructor spent more time on the kernel concept, which is central to understanding why containers are lightweight.

**What a kernel is:**
The kernel is the deepest layer of an operating system — it's the part that talks directly to hardware. Its jobs include:
- Managing the CPU — deciding which program runs when
- Managing memory — giving programs the RAM they request, protecting them from each other
- Managing storage — reading/writing files to disk (HDD, SSD, USB, etc.)
- Managing devices — keyboard, mouse, webcam, network card, speakers
- Managing processes — starting, stopping, and scheduling running programs

**Why programmers don't write to hardware directly:**
Every computer has different hardware. If you had to write code specifically for "the Intel Core i7-13700" or "the WD Black NVMe SSD", software would be completely non-portable. The kernel handles all of this variation. A programmer says "save this data to disk" and the kernel figures out how to talk to whatever storage hardware the machine has.

This is also why you can't just take a program compiled for Windows and run it on Linux — the two kernels have different internal interfaces (system calls).

**Why containers skip the OS but not the kernel:**
A container only needs the *userspace* parts — the libraries, tools, and app-specific code that sits on top of the kernel. It borrows the host machine's kernel directly. This is why:
- Linux containers on Linux: share the Linux kernel → very efficient
- Linux containers on Windows: Docker uses WSL2 to provide a Linux kernel → a small extra layer, but still much lighter than a full VM

Each OS has its own kernel: Windows has the NT kernel, Linux has the Linux kernel, macOS has XNU/Darwin. This is the fundamental reason they're incompatible at the system level.

### 4. 🐳 Docker — Installing and Troubleshooting

#### Installation

```bash
# Install Docker Desktop via winget
winget install Docker.DockerDesktop
```

Two Windows features must be enabled. Search "Turn Windows features on or off":
- ✅ **Windows Subsystem for Linux** (WSL2)
- ✅ **Hyper-V** (or Virtual Machine Platform)

If either is missing, enable it — Docker Desktop will prompt you. Let it restart if it asks.

#### School Computer Troubleshooting

The most common problem on school computers: Docker Desktop installs but won't open or throws an error about permissions. This happens because Docker is installed under the admin/school account (`opilane`), and your personal student account isn't in the `docker-users` group.

**Fix — step by step:**
1. Log out of your own account
2. Log into the school admin account (`opilane` or similar)
3. Open **Local Users and Groups**: search `lusrmgr.msc` or right-click Start → Computer Management → Local Users and Groups
4. Go to **Groups** → find `docker-users`
5. Double-click `docker-users` → click **Add**
6. Click **Advanced** → **Find Now** → search for your account name → select it → OK
7. Click OK to confirm → log out of the admin account
8. Log back into your own account — Docker Desktop should now work

Group membership changes only take effect after logging out and back in. This is a Windows security behaviour, not a Docker bug.

#### Second Potential Issue — `ProgramData\DockerDesktop`

If Docker Desktop is installed but the `ProgramData\DockerDesktop` folder is empty or missing files, the installer may not have completed correctly. Fix:
1. Open PowerShell **as administrator** (right-click → "Run as administrator")
2. Navigate to `C:\ProgramData\` (enable "Show hidden items" in Explorer to see it)
3. Delete the `DockerDesktop` folder
4. Re-run the Docker Desktop installer

### 5. 🌐 Docker Hub — The Image Registry

With Docker working, the instructor did a walkthrough of **Docker Hub** — the primary public registry for Docker images.

**What Docker Hub is:**
The equivalent of npm for JavaScript packages, but for Docker images. Anyone can publish images publicly; official images from major software vendors (Node.js, PostgreSQL, Ubuntu, etc.) are marked as "Docker Official Image".

**What you'll find there:**

| Category | Examples |
|----------|---------|
| **Operating systems** | Ubuntu, Debian, Alpine, Fedora, Rocky Linux |
| **Programming language runtimes** | Node.js, Python, Ruby, Rust, Go, Java |
| **Web servers** | Nginx, Apache |
| **Databases** | PostgreSQL, MariaDB, MySQL, MongoDB, Redis |
| **Tools & utilities** | anything from cowsay to AI image generators |
| **Community images** | Minecraft server, game servers, self-hosted apps |

**Alpine Linux — the tiny base image:**
Alpine is extremely popular as a Docker base image because it's tiny — around 5 MB, compared to Ubuntu's ~100+ MB. Images built on Alpine are much smaller, which means faster downloads and less disk use. The tradeoff is that Alpine uses a different package manager (`apk` instead of `apt`) and some tools work slightly differently.

**Containers exit when their program ends:**
A container exists to run *one program*. When that program finishes, the container stops. A web server container stays up as long as the server is running — it only exits if the server crashes or is stopped. A cowsay container prints its output and exits immediately. This is by design.

### 6. 🐄 Running Your First Container — `cowsay` Demo

With Docker running, the class ran the cowsay demo:

```bash
docker run chuanwen/cowsay
```

**What happened step by step:**
1. Docker looked for the image `chuanwen/cowsay` locally — not found
2. Docker pulled it from Docker Hub automatically (downloading the image layers)
3. Docker created a container from the image
4. The container ran the cowsay program, printed its ASCII cow output
5. Program exited → container stopped automatically

The image was ~334 MB. On subsequent runs, the image is already cached locally — container creation is nearly instant.

### 7. 💡 What Docker Hub Makes Possible — Real-World Examples

The instructor used Docker Hub's breadth to illustrate what's possible once you have Docker, using examples the students could relate to:

**Databases without installation:**
Instead of installing PostgreSQL, MariaDB, or MongoDB on your machine (and potentially having it conflict with other projects), you pull the official Docker image and run it. Stop and delete the container when done — nothing left behind on your system.

```bash
# Example: run a PostgreSQL database
docker run postgres

# Example: run MongoDB
docker run mongo
```

**A Minecraft server in one command:**
The instructor mentioned that you can run a Minecraft multiplayer server with a single `docker run` — no Java installation required, no config files to hunt for. The image creator already packaged everything needed.

**Self-hosted alternatives to cloud services:**
On Docker Hub you can find images for things like:
- Your own **cloud storage** (alternatives to Google Drive)
- Your own **password manager** (e.g. Vaultwarden, a Bitwarden-compatible server)
- AI image generation tools (Stable Diffusion and similar)

The instructor noted that AI image generation via Docker is accessible even on school hardware — it doesn't require a powerful GPU. Simpler models can run on CPU. The instructor had personally pulled a local LLM and tested it, noting that smaller models are quite usable, and interestingly that community-run models don't have the same content restrictions that commercial AI services do — something to be aware of.
