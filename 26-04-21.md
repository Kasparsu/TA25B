### 3. 🖱️ VS Code Source Control GUI — Full Walkthrough

The session spent time on the VS Code Source Control panel as an alternative to the command line, going through every button students are likely to need.

**Visual indicators of Git state:**
- Files turn **brown/yellow** in the Explorer panel when modified but not staged or committed
- A **number badge** appears on the Source Control icon (the branch symbol) showing how many files have uncommitted changes

**The staging workflow in the GUI:**
- **`+` button** on an individual file = `git add <file>`
- **`+` button** on the "Changes" heading = `git add .` (stage everything)
- **`—` button** (minus) on a staged file = unstage it (`git restore --staged <file>`)
- The discard button (↺) next to a file — **be careful** — this discards all changes to that file permanently

**Committing:**
- Type a short message in the box at the top and click **Commit**
- If you click Commit without a message, VS Code opens a text editor — write the subject on line 1, a blank line, then the body if needed; save (`Ctrl+S`) and close the tab to complete the commit
- The commit is local until you **Sync Changes** (push + pull)

**The `…` menu** (three dots next to "Changes"):
- Contains less-common operations: pull, push, fetch, branches, tags, stash, etc.
- The branch indicator at the bottom left of VS Code also allows switching and creating branches

**Why learn the command line if buttons exist?**
The GUI handles everyday simple operations well — and the instructor uses it too. But when things go badly wrong (rebase conflicts, resetting history, reflog recovery), the GUI cannot help. The command line can always do everything. For more complex server work — where you're SSH'd into a remote machine — there is no GUI at all.

### 4. 🟢 Node.js — What It Is and Why We Use It

**JavaScript was originally designed for the browser only.** The browser sandbox deliberately prevents JS from doing server-level things: reading files, making network servers, accessing the filesystem. That's fine for interactive web pages — but what if you want to write backend code in JavaScript?

**Node.js** solves this by taking Google's V8 engine (the JavaScript runtime inside Chrome) and running it outside the browser as a standalone program. On top of V8, Node.js adds the things the browser intentionally withheld: file system access, networking, HTTP servers, etc. The result: JavaScript that runs on the server, in scripts, on the command line — anywhere.

> The name "JavaScript" has nothing to do with Java. It was named for marketing reasons — Java was very popular in 1995 and the name was chosen to ride on that popularity. The two languages share almost no design decisions.

**Installing Node.js:**
```bash
# Install via winget — latest version
winget install OpenJS.NodeJS

# Verify (open a new terminal tab first if fresh install)
node -v     # prints Node.js version
npm -v      # prints npm version
```

After installation, if `node -v` doesn't work, close the terminal and open a new tab — PATH changes require a fresh shell session.

**LTS vs Latest — which to install:**

| Version type | What it means | When to use |
|---|---|---|
| **LTS** (Long Term Support) | Locked features, receives only security + bug fixes for years | Production / client projects — anything that must stay stable |
| **Latest** | Newest features, changes faster | Learning and school — you want modern features |

For school use **Latest**. The caveat: if a fresh major version (`x.0.0`) just dropped, wait a few months before installing — early releases can have breaking bugs. Node follows a pattern where **even-numbered major versions** become LTS. You can see the full release calendar on the release schedule page linked above.

### 5. 🖥️ Writing Your First Node.js Web Server

Create a new file `server.mjs` and paste in the example from the Node.js homepage:

```js
import { createServer } from 'node:http'

const hostname = '127.0.0.1'
const port = 3000

const server = createServer((req, res) => {
  res.statusCode = 200
  res.setHeader('Content-Type', 'text/plain')
  res.end('Hello World\n')
})

server.listen(port, hostname, () => {
  console.log(`Server running at http://${hostname}:${port}/`)
})
```

**Why `.mjs`?**
There are two module systems in JavaScript: **ES Modules** (modern, uses `import`/`export`) and **CommonJS** (older, uses `require()`). The `.mjs` extension tells Node.js explicitly to treat the file as an ES Module. This is what the Node.js docs recommend. You may also encounter `.cjs` for CommonJS files. For most new projects, use `.mjs` or configure your project to default to ESM via `"type": "module"` in `package.json` — more on that in future sessions.

**Running the server:**
```bash
node server.mjs
# Output: Server running at http://127.0.0.1:3000/
```

Open `http://127.0.0.1:3000` or `http://localhost:3000` in the browser — you see "Hello World". The terminal keeps the server running. To stop it: `Ctrl+C`.

**Server keeps running** — unlike most scripts that run and exit, a web server loops continuously waiting for requests. Once started, it runs until you kill it. This is normal and intended.

**Port already in use:** If you try to run two instances at once on the same port, you get `EADDRINUSE`. One process per port, always.

### 6. 🌐 Networking Concepts — IP Addresses, localhost, DNS, MAC

The rest of the session was a practical networking explainer to understand how the server actually communicates.

#### 🔢 IP Addresses

Every device on a network has an IP address — a number that identifies it.

**Three categories matter:**

| Type | Example | What it means |
|------|---------|---------------|
| **Loopback / localhost** | `127.0.0.1` | "This computer itself" — present on every machine on every OS |
| **Local (private) IP** | `192.168.1.x` (home), `172.18.25.x` (school) | Used inside your local network; not reachable from the internet |
| **Public IP** | Varies | What the internet sees; different at school, home, and on mobile |

`127.0.0.1` is known as the **loopback address**. It always means "me". Any process listening on a port of `127.0.0.1` can only be reached from the same machine — nothing external can connect to it.

To find your machine's local IP addresses:
```bash
ipconfig        # Windows (also works in Bash/Git Bash)
```
Look for the **IPv4 Address** under your active network adapter (Ethernet or Wi-Fi).

To find your public IP:

#### 🔡 DNS — Domain Name System

Computers communicate via IP addresses, but humans type names like `google.com`. **DNS** translates between them — it's the phone book of the internet.

When you type a URL:
1. Your computer first checks the local **hosts file** — a plain text file on every OS that maps hostnames to IPs. This is where `localhost → 127.0.0.1` is defined.
2. If not found there, it asks a **DNS server** (usually provided by your router, or public ones like `8.8.8.8`)
3. That DNS server may ask other DNS servers up the chain
4. The IP address comes back instantly, and the connection proceeds

You can verify DNS lookup yourself:
```bash
ping google.com     # shows the resolved IP before pinging
```

**DNS-based ad blocking (side note):**
The instructor mentioned Pi-hole and similar tools — a DNS server you run on your home network that blocks known ad-serving domains before the request even reaches the internet. When a device requests an ad domain, the DNS server returns a dummy address instead. Since this works at the DNS level, it blocks ads on smart TVs, phones, and any device on the network — not just browsers.

#### 🔒 MAC Address

Every network interface (Wi-Fi card, Ethernet port) has a **MAC address** (Media Access Control address) — a hardware identifier burned into the device at manufacture.

While IP addresses can change (your router assigns a different IP every time you reconnect), a MAC address is fixed to the physical hardware. Networks sometimes use MAC addresses for device identification or access control (e.g. a router configured to only allow specific devices).

The `ipconfig` output may show MAC addresses under "Physical Address".

### 7. 🔌 Port Numbers

An IP address gets you to a machine. A **port number** identifies which service on that machine you want. One machine runs many services simultaneously, each on its own port.

Port range: 0–65535.

**Three ranges:**
- **Well-known ports (0–1023)** — reserved for standard protocols. Don't use these for your own dev servers.
- **Registered ports (1024–49151)** — assigned to specific apps; many dev tools live here.
- **Dynamic/private ports (49152–65535)** — use freely.

**Key ports to know:**

| Port | Protocol | Notes |
|------|----------|-------|
| 22 | SSH | Secure remote terminal access |
| 25 | SMTP | Email sending |
| 80 | **HTTP** | Standard web — browser defaults to this |
| 443 | **HTTPS** | Secure web — browser prefers this today |
| 3000 | (dev) | Common Node.js/React dev server default |
| 8000 / 8080 | (dev) | Common alternatives (chosen because they resemble 80) |
| 9000 | (dev) | Also widely used |
| 15137 | Vite | The dev server port used by Vue/Vite projects |
| 25565 | Minecraft | The default Minecraft multiplayer port |
| 65535 | — | Maximum port number |

> 💡 Lower numbers tend to be older, more fundamental protocols — the first services got assigned port 1, the next port 2, etc. This is also why they're considered "well-known": they've been in use since the early days of the internet.

**Why not use port 80 or 443 for development?**
You technically can, but ports below 1024 often require elevated/admin privileges to bind on Linux/macOS. Also, if you want to run multiple dev servers simultaneously, using non-standard ports makes it easy (each server gets its own — 3000, 8080, 9000, etc.). When you go to a website without specifying a port, the browser tries **443** first (HTTPS), then **80** (HTTP). When you type `localhost:3000`, you're explicitly telling it which port.
